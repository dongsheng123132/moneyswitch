# 多台电脑、多个 Agent，共用一个自己托管的支出钱包

笔记本上跑着 Codex，台式机上开着 Claude Code，云服务器上还有一个后台 Agent。它们都能调工具、访问 API。等某个工具开始收费，就会遇到一个新问题：谁能花钱，能花多少，出了问题怎么停？

给每个 bot 单独建钱包，意味着在多台机器之间管理余额、凭据和交易记录。你自己可能已经在用 MetaMask 这样的交互式钱包，但不一定想给每个无人值守的 Agent 都重复一遍配置。

我们正在做的 MoneySwitch，定位就是：**可云自托管的可编程多 Agent 支出钱包。**

## 钱包集中放，花钱权限分开发

MoneySwitch 作为一个服务运行。你创建钱包，放入少量支出资金，再给每个 Agent 发一把单独的 MoneyKey。它看起来像 API Key，代表这把 key 在规则范围内请求付款的权限，不包含钱包私钥。

一种使用方式是：

| Agent | 运行位置 | 拿到什么 |
|---|---|---|
| Codex | 笔记本 | 单独的 MoneyKey、预算和允许访问的域名 |
| Claude Code | 台式机 | 另一把 MoneyKey 和独立额度 |
| 后台 Agent | 云服务器 | 可以单独撤销的 MoneyKey |

它们通过 HTTP 接口向同一个 MoneySwitch 服务请求付款。你在一个地方管理各自的支出权限；每把 key 附带的技能说明告诉 Agent 怎样调用，不需要逐台安装浏览器钱包。

产品目前是**早期自部署软件**，一台实例只替一个出钱的人或组织花钱。这里说的“云钱包”，是你可以把钱包服务部署到自己的云服务器，配置 HTTPS 和持久化存储。你不需要向 MoneySwitch 注册一个账户、把资金存进我们的账户里。

## “可编程”现在具体能做什么

每把 key 可以设置日额度、总额度、单笔上限、允许域名、审批线和过期时间。服务在付款签名之前检查规则。

- 在额度内、访问已允许的域名、金额低于审批线，可以自动付款。
- 金额**达到或超过审批线**，等待人来决定。新的公共域名也要先审批，批准前不会向它发送请求；批准后，该域名会加入这把 key 的白名单。
- 超过日额度、总额度或单笔上限，直接拒绝，人工审批也不能越过这些硬限制。
- 工作结束或不再信任某把 key 时，可以单独撤销。撤销会阻止后续请求，但不会撤回已经签名或结算的付款。

持有这把 key 的人，可以打开审批链接，输入自己的 4–6 位数字确认码，批准或拒绝；登录后台的管理员也可以处理审批。确认码留在人手里，不放进 Agent 的提示词或配置。

Agent 提出付款请求，服务执行额度规则，需要判断时再交给人。这是我们想建立的分工。

## 当前通过 x402 支付

MoneySwitch 目前用 USDC 支付兼容的 x402 API。Agent 带上 MoneyKey 和目标请求，调用 `POST /v1/fetch`。卖家返回 HTTP 402 付款要求后，MoneySwitch 检查权限，签署允许的付款，再带着支付授权重试请求。

当前支持 Monad 和 Base，默认只启用测试网。卖家需要接受支持的链和付款方式，钱包在对应链上也要有余额。它并不能替你支付所有模型 API，也不能直接购买 Claude、Codex 等产品的订阅。它们可以是调用钱包的 Agent，模型本身的订阅账单是另一回事。

我们已经公开过一次 [Qwen 购买 Nansen 数据的实验](https://moneyswitch.dev/blog/qwen-agent-pays-nansen/zh/)，包含 0.09 美元预算内的五笔 Monad 主网交易。它证明了一条具体的支付流程。接下来更想验证的是：把支出收拢到一个服务里，能不能让日常使用多个 Agent 更省心。

## 账单首先要说清楚有没有付钱

后台账单会记录 key、金额、请求网址、链、可用时的交易哈希，以及 `charged: yes | no | maybe`。主网和测试网金额分开显示。

你可以据此找到付款和对应的链上交易，但它不会自动判断这次购买值不值，也不是按任务归集的费用报告。付款结果不明确时，Agent 不能盲目重试，避免再次付钱。

我们也想听听这部分的反馈：这些字段够不够你看懂一次支出？还要回到 Agent 聊天记录里拼出多少上下文？

## 自托管仍然有信任边界

私钥保留在 MoneySwitch 服务端。服务需要能自动签名，所以它仍然是**服务端热钱包**。服务器被攻破，资金依然可能有风险；“不把私钥发给 Agent”并不等于“服务器被攻破也没事”。

服务和 Agent 要有系统权限隔离。如果 Agent 能修改钱包文件或服务数据库，它就可能绕过原本的限制。可以使用独立服务器或适当隔离的服务，并保护管理员入口。以后使用主网时，钱包只放少量支出资金。

先从测试网开始。测试 USDC 没有真实货币价值，已经足够检查付款、审批和撤销流程。

## 这次想请你试真实的工作流程

我们邀请已经在多台电脑上运行 Agent，或同时使用本地与云端 Agent 的开发者来试用。接入两个 Agent，完成一笔小额测试网付款，试一次审批，看看账单，再撤销一把 key。

然后告诉我们：卡在哪一步，你愿不愿意把这个钱包继续用下去，哪些地方仍然需要你亲自充当 Agent 的付款操作员。
