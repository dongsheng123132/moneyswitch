Give your AI an API key for money.

Your AI gets a key with a spending limit. Anything over the approval line waits for a person to approve it, and the private key is never given to the AI. MoneySwitch checks every payment against the key's limits before it signs, then pays x402-priced APIs in USDC.

One MoneySwitch spends for one payer. The administrator issues the keys; there is no sign-up.

x402, plug and play

x402 is powerful — but too hard for most people. We turned it into an API key.

Spend money like you use an API key: the administrator issues a key with limits, and the AI pays with one HTTP call.

Today, with raw x402

PRIVATE_KEY=0x…            // inside your program

const client = new x402Client()
  .register("eip155:10143", new ExactEvmScheme(signer));
const pay = wrapFetchWithPayment(fetch, client);
  • You have to understand HTTP 402, EIP-3009, facilitators and gas
  • A raw private key sits inside every agent
  • No budget, no per-request limit, no approval, no usage view

With MoneySwitch

MONEY_API_BASE=http://127.0.0.1:4020
MONEY_API_KEY=mk_live_…

  • Budgets, per-request limits and approvals checked before every signature
  • Every payment lands on the Bills page: key, amount, URL, chain, transaction hash

How it works

One bearer token between your agent and an on-chain transfer.

AI agents already know one pattern: hold a string with a prefix, put it in an Authorization header. MoneySwitch reuses exactly that pattern for money — no wallet extension, no seed phrase, no signing UI for the agent to click through.

  1. 1

    Agent

    Claude Code, Codex, OpenClaw, Hermes… Reads the skill and calls REST POST /v1/fetch.

  2. 2

    Key

    mk_live_… bearer token, issued by the administrator. Limits are fixed when it is issued; revocable; only its SHA-256 hash is stored.

  3. 3

    Policy

    Per-request limit, max_price, daily / total budget, approval line, host allowlist — all before signing.

  4. 4

    x402

    The API answers HTTP 402 with a price. MoneySwitch signs an EIP-3009 USDC authorization with its local, low-balance wallet.

  5. 5

    USDC

    A facilitator settles the transfer and pays the gas. Of the chains the API accepts, MoneySwitch picks the first one in your list that the wallet can afford — Monad or Base, testnet by default.

  6. 6

    Paid API

    Receives USDC. No MoneySwitch account needed.

The private key lives in an encrypted wallet on the MoneySwitch server. It is decrypted only in the server's memory, never written to disk unencrypted, never logged, and no API returns it; the only wallet secret ever shown is the 12 recovery words, once, when the wallet is created. The server unlocks itself after a restart with a random secret kept next to the wallet, so whoever can read the data folder can spend it: keep only a small float in the wallet, and keep the AI on another machine or system user.

Guardrails

Six checks. All before the signature.

⚿

No private key for agents

The agent only ever holds an mk_live_ key. It cannot reach the wallet or admin routes.

≤

Per-request limit & max_price

Any single payment above the key's cap, or above the caller's max_price, is refused.

◔

Daily & total budgets

Checked and reserved inside one database transaction, so concurrent calls can't overspend.

✋

Human approval line

Above the line, the payment pauses and the AI gets an approval link. An administrator approves it after logging in to the Dashboard; the link carries no token, so the AI can't approve it itself. The agent then retries with the approval_id. A host the key does not list yet asks the same way; approving adds that host to the key.

⌘

Host allowlist

Governs every outbound request, including free ones. A public host that is not listed asks a person first, and nothing is sent until it is approved; private and special-use addresses can never be added that way.

⤺

SSRF guard

Requests to MoneySwitch’s own listening address (127.0.0.1, localhost, 0.0.0.0, ::1) are refused. The match is literal, not a DNS-rebinding defence; see SECURITY.md.

Also: every answer says charged: yes | no | maybe · payments with an unknown outcome count as spent, and the AI must not retry them · secrets are shown exactly once and stored only as SHA-256 hashes · a revoked key stops working immediately. Full threat model in SECURITY.md.

One payer

One MoneySwitch spends for one payer.

You on your own machine, a company issuing keys to its staff's AIs, a company running its own bots: each is one payer, and every coin in the wallet belongs to whoever deployed the server. The administrator issues the keys; there is no sign-up and there are no user accounts.

You

Your own server and wallet, one key per AI of yours, and you approve anything over the line.

A company, for its staff's AIs

The administrator issues each staff member's AI a key with its own limits. The money in the wallet is the company's.

A company, for its own bots

Keys for the company's own agents and services, each with a budget and an approval line.

Letting strangers deposit money and spend it through keys is custody, not a relay — MoneySwitch has no features for it.

Never: fiat on/off-ramps (including buying USDC with fiat or reselling keys), swaps, bridges, issuing tokens, features for receiving payments (a separate product), holding other people's money as a business. Wallet import is not supported: it would put your main wallet's private key on the server.

Quickstart

Run your own server.

$ git clone https://github.com/dongsheng123132/moneyswitch
$ cd moneyswitch
$ pnpm install --frozen-lockfile
$ pnpm build
$ node apps/server-pkg/dist/cli.js --data-dir ./data   # server + Dashboard on :4020
  • The first start prints an administrator token and a one-time sign-in link (valid 30 minutes, single use). Open the link: you are signed in and land on the Wallet page. Set MONEYSWITCH_PUBLIC_URL to the address people reach the server at: approval links and the skill text use it.
  • Wallet: create the wallet, write down the 12 words (shown once), send it a little USDC. It unlocks itself after a restart.
  • Keys: issue one key per AI: daily, total and per-request limits, allowed hosts, approval line, expiry. The key and its skill paragraph are shown once: paste the paragraph into the AI. Limits are fixed once a key is issued; to change them, revoke it and issue a new one.
  • On a testnet-only instance the key form offers a test payment endpoint: the AI makes one test payment (no real value) and reports the transaction hash.
  • Approvals: approve or deny what is over the line. Bills: every payment with key, URL, chain, transaction hash and charged yes / no / maybe.
  • On a server: Docker Compose and HTTPS with persistent volume, health check, backup and rollback, see deploy/README.zh-CN.md. Do not run the server and the AI on the same machine under the same system user: the AI could edit the database and get around the limits.

Requires Node.js 22+ and pnpm. Testnets only by default (Monad testnet, Base Sepolia); choosing a mainnet means real USDC. Everything else is in the README.
