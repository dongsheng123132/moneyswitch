How it works

Program spending with the same pattern as an API key.

An agent needs the service URL, a MoneyKey and the ability to make HTTP requests. MoneySwitch checks the key’s policy and handles wallet signing. x402 is the payment mechanism behind the API.

  1. 1

    Agent

    An agent on your laptop or cloud server reads the skill and calls REST POST /v1/fetch.

  2. 2

    MoneyKey

    A revocable mk_live_… token issued by your administrator. Each key has its own limits; the service stores only its SHA-256 hash.

  3. 3

    Policy

    Check per-request, daily and total limits, max_price, allowed hosts and the approval threshold before signing.

  4. 4

    x402

    The API returns HTTP 402 with a price. MoneySwitch signs a USDC authorization from the small spending wallet on your server.

  5. 5

    USDC

    A facilitator settles the transfer and pays the gas. Of the chains the API accepts, MoneySwitch picks the first one in your list that the wallet can afford — Monad or Base, testnet by default.

  6. 6

    Paid API

    Receives USDC. No MoneySwitch account needed.

The service holds an encrypted hot wallet and the secret needed to unlock it after a restart. Anyone who can read the server’s data directory can use the wallet; anyone who can change its database can bypass policy. Separate agents from that machine or system user, restrict data access, and keep only a small balance. A MoneyKey does not grant wallet export or administrator access through the API.

Spending controls

A separate spending policy for each agent.

⚿

Revocable MoneyKeys

Give the agent a MoneyKey, not the wallet’s private key. Revoke that key to stop future API use. Keep wallet files and administrator credentials outside the agent’s access.

≤

Per-request limit & max_price

Any single payment above the key's cap, or above the caller's max_price, is refused.

◔

Daily & total budgets

Checked and reserved inside one database transaction, so concurrent calls can't overspend.

✋

Human approval line

At or above the threshold, payment waits for approval. The person holding that key uses its 4–6 digit PIN, or an administrator signs in to approve. Keep the PIN with the person, not the agent. The agent then retries with approval_id. New public hosts also require approval; approval adds the host to that key.

⌘

Host allowlist

Governs every outbound request, including free ones. A public host that is not listed asks a person first, and nothing is sent until it is approved; private and special-use addresses can never be added that way.

⤺

SSRF guard

Requests to MoneySwitch’s own listening address (127.0.0.1, localhost, 0.0.0.0, ::1) are refused. The match is literal, not a DNS-rebinding defence; see SECURITY.md.

Also: every answer says charged: yes | no | maybe · payments with an unknown outcome count as spent, and the AI must not retry them · MoneyKey tokens are shown exactly once and stored only as SHA-256 hashes · a revoked key stops working immediately. Full threat model in SECURITY.md.

Your deployment

Self-host in the cloud. Keep control of the wallet.

One deployment spends for one payer: you or your organization. Run MoneySwitch on infrastructure you control, fund its wallet with your own USDC, and issue keys to your agents. This is self-hosted software, not a hosted wallet account.

Across your computers

Your laptop and desktop agents connect to the same service. Each gets a different key and spending budget.

Local and cloud agents

A cloud job uses the same wallet as your local agents through HTTP. Serve the wallet over HTTPS and keep its data isolated.

An organization’s own spending

Issue keys for staff agents and company bots. The organization funds the wallet; each key has its own limits and payment records.

Self-hosting means you operate the wallet service and protect its data. MoneySwitch does not hold funds on your behalf.

Scope today: your own spending wallet and x402 API payments. No customer deposits, fiat on/off-ramps, swaps, bridges or wallet imports. Your main wallet stays separate.

Quickstart

Deploy once. Connect your agents.

$ git clone https://github.com/dongsheng123132/moneyswitch
$ cd moneyswitch
$ pnpm install --frozen-lockfile
$ pnpm build
$ node apps/server-pkg/dist/cli.js --data-dir ./data   # server + Dashboard on :4020
  • The first start prints an administrator token and a one-time sign-in link (valid 30 minutes, single use). Open the link: you are signed in and land on the Wallet page. Set MONEYSWITCH_PUBLIC_URL to the address people reach the server at: approval links and the skill text use it.
  • Wallet: create a dedicated spending wallet and write down the 12 recovery words, shown once. Start with test USDC on a testnet. It unlocks itself after a restart.
  • MoneyKeys: create one per agent with per-request, daily and total limits, allowed hosts, approval threshold and expiry. Keep the approval PIN with the person. Copy the key’s skill paragraph into the agent. To change a key’s limits, revoke it and issue a new one.
  • With Monad testnet enabled, a testnet key can use the test payment endpoint, even if mainnets are also enabled. When that endpoint is selected, the generated skill already asks for one test payment (no real value). Observe the result and transaction hash; do not ask the agent to pay again.
  • Approvals: a payment at or above its threshold waits for the key’s PIN holder or a signed-in administrator. Bills: review each payment’s key, amount, URL, chain, transaction hash and charged yes / no / maybe.
  • On a server: Docker Compose and HTTPS with persistent volume, health check, backup and rollback, see deploy/README.zh-CN.md. Do not run the server and the AI on the same machine under the same system user: the AI could edit the database and get around the limits.

Requires Node.js 22+ and pnpm. Testnet by default; enabling a mainnet means real USDC. See the README for deployment options.
