Your agents run everywhere.
Can their spending share one wallet?

MoneySwitch is a programmable spending wallet for multiple AI agents, self-hosted on your own server. Try it with your agents and tell us what helps and where you get stuck.

Try it on a testnet ↓Share feedback

You currently need your own deployment; there is no public hosted-account signup. The trial uses test USDC with no real value. Bring a runtime and follow the wallet's faucet instructions to obtain test tokens. This is not a dollar-denominated API credit offer.

Who this is for

  • You use Codex, Claude Code, OpenClaw or agents you built yourself.
  • Your agents run across computers and cloud servers, and need paid services.
  • You can run a self-hosted service and want to try x402 API payments.

One agent is enough to start. Feedback about a failed setup is useful too.

What you can try

  • One wallet you control, with a separate budget-limited MoneyKey per agent.
  • Human approval at or above a configured payment threshold.
  • A shared payment history and the ability to revoke a key.

Payments currently cover supported USDC / x402 services. This does not pay arbitrary websites or existing AI subscriptions.

A small end-to-end experiment

Give two agents a key each

  1. Run your own wallet service

    Follow the Docker + HTTPS deployment guide (Chinese) or the source quickstart. Isolate the service from your agents' machines or system permissions so the agents can only access it over the network with MoneyKeys.

    Keep the administrator sign-in link from the first start private. Create a wallet, save its recovery phrase yourself, and use the wallet page's faucet instructions to obtain Monad testnet USDC. You do not need mainnet funds for this trial.

  2. Issue a testnet key to agent A and agent B

    On the Keys page, use distinct names such as laptop-codex and cloud-claude. Select Testnet for both and keep the test payment endpoint enabled. Here is one suggested policy; all amounts are test USDC:

    SettingAgent AAgent B
    Total / daily budget0.05 / 0.050.05 / 0.05
    Per-request limit0.020.02
    Approval thresholdLeave empty0.01

    Give each agent its own skill paragraph and check that it can reach your HTTPS service URL. Keep the approval PIN with a person. Do not put a PIN, administrator token or recovery phrase in an agent's skill. With one agent, try the two keys one after another.

  3. Observe payment and approval

    When the test endpoint is enabled, the skill instructs the agent to check its budget and make one 0.01 test USDC payment to https://app.moneyswitch.dev/x402-testnet/check. Do not repeat that payment manually.

    A should pay within its limits. B reaches its approval threshold and should return an approval link first. Use that key's PIN to approve, or approve as the administrator in the dashboard; the agent then follows the skill to continue the request. Save the successful transaction hash. If you see charged: maybe or a timeout, check Bills before taking further action; do not retry automatically.

  4. Check the history and revoke a key

    Look for each key in Bills: amount, URL, chain, charge status, and a transaction hash for a confirmed payment. Revoke A's key and ask A only to check GET /v1/status; it should be rejected. No further payment is needed.

    Note the least clear step, any error, and a real service you would want an agent to buy. If you cannot get test tokens or finish deployment, report that too.

Before you start

Who holds this cloud wallet?

You run the service and manage the wallet and its data on your own server. Agents receive budget-limited access keys. Anyone who can read the server's wallet data and unlock file can use the wallet; protect the server and treat any future mainnet deployment as a small spending wallet.

Does every agent get a wallet address?

Agents share one payer's wallet, with separate keys and limits. A key's budget is a spending ceiling, not a separately funded balance. The same wallet address has independent balances on each supported chain.

Do I have to share a post, leave a positive review or pay?

Feedback has no sharing or positive-review requirement. No cash, API-credit or badge reward is promised. Test tokens have no real value; your own hosting or runtime may incur costs.

What is still missing?

Per-payment purpose notes and task-level cost reports are not implemented. Child keys have backend APIs but no creation UI. Integration is through a skill and HTTP, without MCP or a public multi-tenant hosted service.
