Propose a contribution ↗

Your first pull request

From your fork to upstream main

  1. Choose one small problem

    Start with something you can reproduce or explain in a sentence. Read CONTRIBUTING.md. For deployment or payment behavior changes, also read SPEC.md and discuss substantial changes first.

  2. Fork, then clone your own repository

    Click Fork. Replace YOUR_GITHUB_USER below with your GitHub username, or copy the clone URL from your fork’s Code menu.

    git clone https://github.com/YOUR_GITHUB_USER/moneyswitch.git
cd moneyswitch
git remote add upstream https://github.com/dongsheng123132/moneyswitch.git
git switch -c docs/my-first-fix

  3. Edit the source and verify the result

    Change only what your fix needs. The homepage, trial and contribution pages live in site/. Blog text lives in docs/blog/; after editing it, run node scripts/build-blog.mjs and include the generated pages.

    Follow the test requirements in CONTRIBUTING.md. Preview website changes in both languages and at phone width. Say what you actually checked, and what you could not check.

  4. Commit and push to your fork

    Review the diff first. Replace the example path with the files you intentionally changed; keep credentials and local wallet data out of the commit.

    git diff
git add path/to/changed-file
git commit -m "docs: clarify the trial setup"
git push -u origin docs/my-first-fix

  5. Compare across forks and submit

    Open the upstream comparison and choose compare across forks. Use dongsheng123132/moneyswitch with base: main; use your fork as the head repository and docs/my-first-fix as the compare branch.

    Review the diff, explain what changed and how you verified it, and personally read the CLA before checking its agreement box. Submitting a PR starts maintainer review; it does not mean the change is approved or merged.

A helpful PR explains the result

“The trial guide repeated a payment instruction. I clarified that the generated skill already makes that request, and checked both language pages.” That is more useful than “improve docs.” Include screenshots when they help explain a visual change.

A few things to know

Do I need to buy tokens or use mainnet to contribute?

No mainnet payment is required. Start with the testnet trial or a documentation issue. Follow the contribution guide for offline tests; live-payment testing uses your own test wallet, never a maintainer’s shared wallet.

What is this wallet’s scope?

One deployment spends for one payer using budget-limited MoneyKeys. Payments currently cover supported x402 APIs in USDC. This is a self-hosted hot wallet: access to its wallet data and unlock file grants access to funds. Changes to payment policy, deployment or trust boundaries need to follow the spec.

Who agrees to the CLA?

The contributor personally reads CLA.md and checks the PR agreement box if they agree. Reading this page does not sign anything, and the guide does not accept terms on your behalf.

Does a PR qualify for a reward?

Rewards may be offered at our discretion based on participation and feedback, with details announced separately. Opening or merging a PR does not guarantee a reward or a fixed amount.

What should stay out of a public issue or PR?

MoneyKeys, approval PINs, recovery phrases, private keys, administrator tokens and sign-in links, raw logs containing credentials, and wallet data. Share redacted examples. Report vulnerabilities through private security reporting, following SECURITY.md.

A clear report is a contribution too.

You do not need a fix to tell us where setup failed or which agent workflow is missing.
